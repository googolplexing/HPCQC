lumi-hpc-qc

Version 1.0.0b1 · 2026-03-26 · 55 Python files · 4,615 lines · LUMI (CSC Finland) + VTT Q50

A modular framework for running Variational Quantum Algorithms on the LUMI supercomputer (AMD MI250X GPUs) and the VTT Q50 quantum processor via FiQCI. Designed so researchers can add new physics models, ansatze, optimizers, and error mitigation strategies as drop-in plugins without touching the core orchestration code.

Single configuration point: All deployment-specific paths (containers, wrappers, SLURM account) live in one file: env.sh. Edit it once; every script picks up the change. Experiment configs (YAML) contain only physics and algorithm parameters — zero deployment paths.

Motivation & background

This project evolved from a proof-of-concept (lumi_vqa) that demonstrated VQE workflows on LUMI GPUs. While the PoC validated the science — convergence of 5 physics models, adiabatic initialization, parameter-shift gradients — it was monolithic Python scripts with hardcoded paths, no plugin system, no crash recovery, and no separation of concerns.

The V1.0 redesign addresses four priorities identified during PoC testing:

  1. Checkpointing: A 2-hour Heisenberg job that crashes at minute 110 should be resumable, not lost.
  2. Multi-backend: The same experiment config should run on GPU simulation, CPU MPS, or real quantum hardware with a single field change.
  3. Plugin extensibility: Researchers adding a new Hamiltonian should not need to understand SLURM scripts, container bindings, or checkpoint serialization.
  4. Automated orchestration (Mode B): Long-running experiments should survive user disconnections and auto-retry from checkpoint on node failures.

5-layer architecture

All arrows point downward — no upward dependencies. Layer 3 never imports from Layer 2. Layer 4 never imports from Layer 3. This is Dependency Inversion in practice.

1
CLI — Config files (YAML), SLURM submission helpers, status monitoring. The only layer researchers touch directly.
↓
2
Orchestration — Workflow engine (VQE loop, adiabatic ramp), job scheduler (SLURM submit/monitor), checkpoint manager (save/resume state), controller (Mode A interactive / Mode B automated).
↓
3
Backends — Pluggable execution: Aer GPU (statevector/density matrix), Aer CPU (MPS), IQM QPU (Q50 via FiQCI), future QCut + CUDA-Q. Each implements the same Backend ABC.
↓
4
Plugins — 6 sub-packages (hamiltonians, ansatze, optimizers, gradients, initializers, error_mitigation). Auto-discovered. Researchers add a Python file, it's available.
↓
5
Data — Experiment tracker, provenance collector (all imported modules), timing (3 formats: human/benchmark/ML), result store (JSON with numpy support).

Dependency map

User Interface  →  Orchestration  →  Execution Backends
                        ↓                    ↓
                   Checkpoint Mgr      Plugin Registry
                        ↓                    ↓

Key principle: the workflow engine calls plugin interfaces (ABCs), never concrete implementations. Adding a new Hamiltonian means writing one class that inherits from HamiltonianBuilder — zero changes to workflow, backend, or CLI code.

Abstract interfaces (ABCs)

The framework defines 9 abstract base classes. Every plugin implements exactly one of these. The workflow engine calls only these interfaces — never concrete classes.

Metadata-driven wiring

The AnsatzMetadata dataclass declares compatibility constraints that the workflow uses to auto-select plugins:

@dataclass
class AnsatzMetadata:
    num_parameters: int
    gradient_compatibility: str   # "parameter_shift", "finite_difference", "both"
    preferred_initializer: str    # "random", "zero", "adiabatic"
    requires_decomposition: bool  # whether backend must decompose before execution

Example: UCCSD sets gradient_compatibility="finite_difference" and preferred_initializer="zero". The workflow reads this and automatically selects the right gradient and initializer — no manual wiring.

env.sh — deployment configuration

One file controls all deployment-specific settings. No other file in the project contains hardcoded paths.

# ── SLURM account ──
export HPCQC_ACCOUNT="project_462001289"
export SBATCH_ACCOUNT="${HPCQC_ACCOUNT}"

# ── Container paths ──
export HPCQC_GPU_CONTAINER="/path/to/gpu-container.sif"
export HPCQC_CPU_CONTAINER="${HPCQC_GPU_CONTAINER}"  # or separate CPU image

# ── Container launch wrappers ──
export HPCQC_GPU_WRAPPER="/path/to/run-singularity-with-gpu-affinity"
export HPCQC_CPU_WRAPPER="/path/to/run-singularity"

# ── GPU affinity mask (LUMI MI250X) ──
export HPCQC_GPU_MASK="mask_cpu:0xfe000000000000,..."

# ── SLURM partitions ──
export HPCQC_GPU_PARTITION="standard-g"
export HPCQC_CPU_PARTITION="standard"
export HPCQC_SMALL_PARTITION="small"
To deploy on a different system: Edit env.sh with your container path, wrapper script, and account. Then source env.sh && sbatch tests/test_smoke.sh. If the smoke test passes, everything works.

Container wrappers

LUMI requires Singularity containers launched through specific wrapper scripts that handle filesystem bindings and GPU affinity.

CPU wrapper (run-singularity)

Reads bind mount lists from inside the container, sets up MPICH. Used for CPU-only nodes (standard partition, MPS simulation).

GPU wrapper (run-singularity-with-gpu-affinity)

Same as CPU wrapper plus: maps each MPI rank to a specific GCD on the MI250X via ROCR_VISIBLE_DEVICES. The ordering 4 5 2 3 6 7 0 1 matches NUMA-to-GCD topology so each rank talks to its closest GPU.

Mode B (automated orchestration)

Mode B runs a lightweight bash controller on a minimal CPU node. The controller submits the actual VQE as a child GPU job, monitors it via squeue, and auto-retries from the latest checkpoint on failure.

# Launch Mode B
source env.sh
./tests/launch_mode_b.sh configs/byo_tfim_8q.yaml --walltime 00:15:00

# Monitor both jobs
squeue --me
# You'll see:
#   11111 small      modeb_controller  RUNNING  0:30
#   22222 standard-g modeb_child_a1    RUNNING  2:15

# Check controller output
tail -f slurm_logs/modeb_ctrl.o<controller-jobid>

Controller lifecycle:

  1. Generates child VQE script (matching the LUMI launch pattern)
  2. Submits child to standard-g via sbatch
  3. Polls squeue every 30 seconds, reads progress files from shared filesystem
  4. On child COMPLETED → collects results → done
  5. On child FAILED/TIMEOUT → finds checkpoint → generates resume script → resubmits (up to 3 retries)
  6. On child CANCELLED → aborts

Checkpoint & resume

The VQE workflow saves checkpoints at configurable intervals during optimization. Each checkpoint contains: current parameters, best energy, best parameters, iteration count, and timestamp.

Checkpoint format:

checkpoints/<experiment_id>_iter000050.json
{
  "params": {"__ndarray__": true, "data": [0.12, -0.45, ...], "dtype": "float64"},
  "best_energy": -7.619,
  "best_params": {"__ndarray__": true, "data": [...]},
  "iteration": 50,
  "_checkpoint_meta": {
    "iteration": 50,
    "experiment_id": "abc123_12345",
    "timestamp": "2026-03-26T09:15:30+00:00"
  }
}

Resume rebuilds the full pipeline (_setup(): registries, Hamiltonian, ansatz, backend) then calls _optimize() with restored parameters — the optimizer continues from where it left off.

Plugin system overview

The plugin registry auto-discovers classes in each sub-package. To add a new plugin:

  1. Create a Python file in the right directory (e.g. src/lumi_hpc_qc/plugins/hamiltonians/my_model.py)
  2. Define a class that inherits from the base ABC
  3. Set the name class attribute
  4. Implement the required methods

That's it. No registration, no config changes. The registry finds it automatically.

Adding a new Hamiltonian

# src/lumi_hpc_qc/plugins/hamiltonians/my_model.py

from lumi_hpc_qc.plugins.hamiltonians.base import HamiltonianBuilder
from lumi_hpc_qc.types import ExperimentConfig, HamiltonianMetadata
from qiskit.quantum_info import SparsePauliOp
import numpy as np

class MyModelHamiltonian(HamiltonianBuilder):
    name = "my_model"                      # ← used in YAML: model: my_model
    description = "My custom physics model"

    def build(self, config: ExperimentConfig):
        p = config.model_params
        # Build your SparsePauliOp here
        terms = [("ZZ", p.get("coupling", 1.0)), ("XI", p.get("field", 0.5))]
        ham = SparsePauliOp.from_list(terms).simplify()
        meta = HamiltonianMetadata(
            num_qubits=ham.num_qubits,
            pauli_term_count=len(ham),
            description="My model description",
        )
        return ham, meta

    def exact_ground_energy(self, hamiltonian):
        if hamiltonian.num_qubits > 24:
            return None  # too expensive
        return float(np.real(np.linalg.eigvalsh(hamiltonian.to_matrix())[0]))

    def adiabatic_parameter_name(self):
        return "coupling"  # or None if adiabatic init doesn't apply

    def build_at_parameter(self, value, config):
        config.model_params["coupling"] = value
        ham, _ = self.build(config)
        return ham

Adding a new ansatz

# src/lumi_hpc_qc/plugins/ansatze/my_ansatz.py

from lumi_hpc_qc.plugins.ansatze.base import AnsatzBuilder
from lumi_hpc_qc.types import AnsatzMetadata, ExperimentConfig
from qiskit import QuantumCircuit
from qiskit.circuit import ParameterVector

class MyAnsatz(AnsatzBuilder):
    name = "my_ansatz"

    def build(self, num_qubits, config):
        reps = config.ansatz_params.get("reps", 2)
        n_params = num_qubits * reps
        params = ParameterVector('θ', n_params)
        qc = QuantumCircuit(num_qubits)

        idx = 0
        for r in range(reps):
            for q in range(num_qubits):
                qc.ry(params[idx], q)
                idx += 1
            for q in range(num_qubits - 1):
                qc.cx(q, q + 1)

        meta = AnsatzMetadata(
            num_parameters=n_params,
            parameter_names=[f"p{i}" for i in range(n_params)],
            gradient_compatibility="parameter_shift",  # or "finite_difference"
            preferred_initializer="random",             # or "zero", "adiabatic"
            requires_decomposition=False,
        )
        return qc, meta

Adding a new optimizer

# src/lumi_hpc_qc/plugins/optimizers/my_optimizer.py

from lumi_hpc_qc.plugins.optimizers.base import OptimizerStrategy
from lumi_hpc_qc.types import ExperimentConfig, IterationRecord, OptimizeResult
import numpy as np

class MyOptimizer(OptimizerStrategy):
    name = "my_optimizer"
    requires_gradient = False  # True if your optimizer needs gradients

    def minimize(self, cost_fn, x0, grad_fn=None, config=None, callback=None):
        # Your optimization logic here
        maxiter = config.optimizer_params.get("maxiter", 100)
        best_x, best_f = x0.copy(), cost_fn(x0)

        for i in range(maxiter):
            # ... your optimization step ...
            if callback:
                callback(IterationRecord(iteration=i+1, energy=best_f, parameters=best_x))

        return OptimizeResult(x=best_x, fun=best_f, nfev=maxiter, nit=maxiter, success=True)

Bring-Your-Own (BYO) guide

The BYO model lets you run VQE on any Hamiltonian without writing Python code. Just provide a JSON file:

{
  "description": "My custom 4-qubit Hamiltonian",
  "pauli_terms": [
    {"label": "IIZZ", "coeff_real": 0.5, "coeff_imag": 0.0},
    {"label": "ZZII", "coeff_real": 0.3, "coeff_imag": 0.0},
    {"label": "XIXI", "coeff_real": -0.2, "coeff_imag": 0.0}
  ]
}

Or the simpler list format:

{
  "pauli_terms": [["IIZZ", 0.5], ["ZZII", 0.3], ["XIXI", -0.2]]
}

Reference it in your YAML:

model: byo
model_params:
  hamiltonian_file: examples/my_hamiltonian.json
ansatz: su2
ansatz_params:
  reps: 3

Known research-level issues

FH / Heisenberg — HVA local minima

The HVA ansatz at 3 layers captures only a fraction of the correlation energy on 2D lattices. The adiabatic ramp produces a smooth, monotonically decreasing energy curve, but tracks a local minimum rather than the global one. The literature (Wiersema et al., PRX Quantum 1, 020319, 2020) shows this requires either deeper circuits, different ansatze (ADAPT-VQE), or symmetry-exploiting initializations. These are exactly the kind of improvements that can be plugged in as new ansatz/initializer plugins.

H2 UCCSD — parameter binding after decomposition

The qiskit-nature UCCSD circuit after 10 rounds of .decompose() loses its parameterization — the energy is constant regardless of parameter values. The fix path is to use Qiskit's Estimator primitive (which handles circuit compilation internally) or avoid full decomposition. This would be a new backend evaluation strategy plugin.

Container binding requirements

The LUMI container has a built-in runscript that validates bindings. Direct singularity exec fails — must use the GPU or CPU wrapper scripts that extract bind mount lists from inside the container.
